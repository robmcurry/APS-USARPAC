Bottom line

PRS-VIF's structural formulation checks out at every scale actually tested — the real 50-node, 96-vehicle network builds and its LP relaxation solves cleanly through Ω=50 scenarios, matching every dimension the dissertation's case study specifies. The target scale, Ω=100, does not: four independent attempts to build or solve it have now failed, all tracing to the same underlying cause — this laptop's 18 GB of RAM, not a defect in the model or the code that builds it.

A first real MIP attempt at a reduced but still CVaR-meaningful scale (Ω=30, β=0.8) got further than anything before it — a clean, twice-reproduced root-relaxation solve — before running out of memory during Gurobi's crossover step, before branch-and-bound ever started. Nothing tried so far (bulk constraint construction, fewer solver threads, disk-backed node storage) has closed the gap. The two paths that plausibly would are more RAM, or a smaller and better-conditioned formulation.

01

Why Ω=100 isn't just a nice round number

CVaR's tail size is (1 − β) × N. At the dissertation's calibrated β=0.9, that arithmetic is unforgiving: N=100 gives a tail of 10 scenarios — enough for the risk measure to actually average a set of bad outcomes. N=10 gives a tail of exactly 1 — CVaR stops being a conditional average and collapses to a single worst-case draw, a degeneracy already observed by accident in earlier unit testing. N=50 gives a tail of 5: non-degenerate, but thin.

So reducing the scenario count isn't a free way around the memory ceiling — it changes what the objective means. The one deliberate exception tried here is β=0.8, N=30 (tail = 6, comparable richness to N=50 at β=0.9), chosen specifically to stay inside the memory-safe range while keeping CVaR non-degenerate. See §4.

03

Four attempts at Ω=100

All four used the real network at full scale (≈14.2M variables, ≈5.1M constraints, extrapolated). None reached a completed build. Two hit a genuine multi-hour resource thrash; one was a false alarm from an over-cautious safety script; one hit a real ceiling mid-growth.

Attempt 1 — unmonitored background runThrashed

Ran 80+ minutes of CPU time without ever reaching a completed build. Process memory stayed flat at 2.8–3.5 GB the entire time — no forward progress, not the healthy growth curve seen at every smaller Ω. System swap climbed to 4.1 of 5.0 GB used; free system RAM fell to 0.06 GB. Terminated by the operating system for system-wide low memory.

Attempt 2 — same code, actively monitoredThrashed

Memory grew normally to ~7 GB in the first 90 seconds — matching the confirmed healthy pattern — then plateaued for over three hours with CPU pegged and zero further progress: the same thrash signature as Attempt 1, this time observed live rather than inferred after the fact. Self-terminated as a manual kill was being issued.

04

Did rewriting the construction code help?

The two constraint families that scale as Ω×|vehicles|×|arcs| — together the overwhelming majority of the model's rows — were originally built with one Python call per row (4.57M individual calls at Ω=100). These were converted to Gurobi's bulk-insert API, which hands the solver the whole family in a single call.

Verified mathematically identical: rebuilt at Ω=3, every variable and constraint count and the LP-relaxation objective (5,074,641,919.5340) matched the pre-conversion run to the decimal.

Made no measurable difference: at Ω=50, build and relax times were statistically unchanged from the per-row version.

06

Diagnosis

  • The formulation itself is sound: every scale from Ω=3 to Ω=50 builds and LP-relaxes correctly, and the Ω=30 MIP's root relaxation reproduces the identical objective across two different solver configurations.
  • The obstacle is resource capacity on this specific machine — 18 GB of RAM, several of which are already tied up by residual swap from earlier attempts — not a bug in the model or in the code that constructs it.
  • Two distinct pressure points showed up at two different scales: outright construction memory at Ω=100 (never completed, LP or MIP), and solver-internal presolve/barrier/crossover memory at just Ω=30 once integrality is turned on.
  • Branch-and-bound — arguably the phase most likely to need real headroom for a problem this size — has never actually run. Every failure so far happens before it starts.
  • An 11-order-of-magnitude spread in the model's coefficients (5×10⁻⁴ to 2×10⁷), visible in Gurobi's own presolve report, is a plausible contributor to Run 2's crossover instability — traceable to very large "obviously non-binding" placeholder constants (10⁶–10⁹) standing in for two not-yet-calibrated parameters.
07

Recommendations

  1. More RAM.A machine with meaningfully more headroom — a lab machine or a cloud instance — is the most direct route to an actual Ω=100 result, and the only option that requires no changes to the formulation.
  2. Shrink the placeholder coefficients.Replace the 10⁶–10⁹ "non-binding" placeholders (node-handling capacity; one arc-throughput fallback) with smaller values that are still safely non-binding. Untested, but a cheap, targeted response to the specific instability Run 2 showed.
  3. Try disabling crossover.Gurobi's Crossover=0 is a one-line, no-model-change test of whether branch-and-bound can proceed directly from the interior-point solution, skipping the phase that failed in Run 2.
  4. Further construction-code rewrites.Already tested and ruled out — the bulk-insert conversion (§4) made no measurable difference at any scale tried.
  5. Reducing the scenario count alone.Not a workaround — per §1, it changes what the CVaR objective means, not just how expensive it is to compute.
